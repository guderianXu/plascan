# ASP 对齐密集点云优化设计

## 背景

当前 `StereoDenseCloudPipeline` 已能生成 `PC.tif` 和 `PC.ply`，并能与 ASP `run-PC.tif` 对比，但现有测试对结果距离 ASP 仍较远：PlaScan 有效点约 193.6 万，ASP 有效点约 1109.3 万，覆盖率约为 ASP 的 17.5%。因此当前状态不能视为“优化完成”。

同时，GUI 的 `工作流程 -> 创建密集点云` 仍使用 `SimplePointCloudDialog` 和旧的 `DepthMapGenerator` 路线，尚未接入 ASP 对齐管线。Dialog 必须等核心结果达标后再更新，避免把未达标能力包装成完成品。

## 目标

先针对 `data/stereo_test_20260426` 现有双视图测试对，迭代优化自研密集点云管线，使结果接近 ASP。ASP 只作为基准参考，不作为生产后端调用。

停止条件采用严格 ASP 对齐标准：

- PlaScan 有效点覆盖率 ≥ ASP 有效点数的 80%。
- PlaScan 到 ASP 点云的 3D 最近邻中位距离 ≤ 0.001。
- PlaScan 到 ASP 点云的 3D 最近邻 P95 距离 ≤ 0.01。

满足以上条件后，才进入 GUI dialog 更新阶段。

## 非目标

- 不把 ASP 命令行工具包装成 PlaScan 的生产后端。
- 不提前修改 GUI dialog。
- 不声称当前优化泛化到所有数据集；第一阶段只对现有测试对负责。
- 不做与 ASP 对齐无关的重构。

## 设计原则

1. **ASP 思路优先**：优先采用 ASP stereo 的核心思路，包括极线校正、视差域密集匹配、左右一致性、噪斑过滤、逐像素三角化和 ASP 风格 `PC.tif` 输出。
2. **速度优化建立在 ASP 思路之上**：先保证流程方向正确，再通过 CUDA、缓存、ROI、并行、可配置降采样和早停优化速度。
3. **每轮只改一个主要变量**：每次迭代必须能说明指标变化来自哪个参数或算法步骤。
4. **用指标驱动判断**：每轮都运行同一基准，记录 coverage、median、P95 等指标，不靠肉眼或单次日志判断。

## 总体架构

优化工作分为两个阶段。

### 阶段一：核心质量达标

新增或整理一个基准驱动迭代层，围绕 `StereoDenseCloudPipeline` 工作：

```text
现有测试对 + ASP run-PC.tif
        |
        v
运行自研 ASP 对齐密集点云管线
        |
        v
生成 PlaScan PC.tif / PC.ply
        |
        v
读取 ASP run-PC.tif
        |
        v
计算结构化指标
        |
        v
PASS: 冻结参数并进入 GUI 阶段
FAIL: 根据指标定位下一处参数或算法改动
```

### 阶段二：GUI 接入

只有阶段一达标后，才更新 `SimplePointCloudDialog` 和工作流程入口。GUI 必须明确标注该能力是“双视图 ASP 对齐模式”，除非后续另行完成多视图泛化。

## 组件设计

### 1. ASP 对比指标模块

职责：读取 PlaScan `PC.tif` 和 ASP `run-PC.tif`，输出结构化指标。

核心指标包括：

- ASP 有效点数。
- PlaScan 有效点数。
- coverage ratio。
- PlaScan 点落入 ASP bbox 的比例。
- nearest-neighbor mean / median / P90 / P95 / max。
- mean offset。
- PASS / FAIL 结论。

该模块应从当前 `stereo_pipeline_test.cpp` 中散落的统计逻辑中抽出，避免每次只能人工读 `printf`。

### 2. 基准运行器

职责：固定运行 `data/stereo_test_20260426` 测试对，调用管线并调用指标模块。

输出必须包含：

- 控制台摘要，便于快速迭代。
- JSON 指标文件，便于对比多轮结果。
- 当前使用的关键参数快照。

### 3. 可调配置层

职责：把当前硬编码的过滤和匹配参数显式配置化，支持基准运行器控制。

首批配置项：

- PatchMatch iterations。
- patch size。
- confidence threshold。
- zNear / zFar 估计策略与扩展比例。
- 左右一致性阈值。
- 局部一致性窗口与深度比例阈值。
- IQR 过滤开关与倍数。
- speckle 过滤开关与区域阈值。
- triangulation max error。
- 输出是否保留中间深度图、视差图和 mask。

### 4. ASP 风格核心管线

当前代码与既有设计文档存在偏差：文档描述的是“极线校正 + 视差域处理 + 逐像素三角化”，而现有实现主要是“原始相机深度 PatchMatch + 后过滤”。如果调参无法接近 ASP，必须补齐 ASP 风格流程。

优先补齐的步骤：

1. 基于相机或匹配点做极线校正，输出 rectified left/right 以及反变换。
2. 在校正图像上进行密集匹配，使用视差或等价的水平搜索约束。
3. 进行左右一致性检查，阈值使用像素视差差异，而不是仅比较深度比例。
4. 使用 speckle / 连通域过滤替代过强的全局 IQR 过滤。
5. 对有效视差逐像素反变换回原图坐标，用左右相机射线交汇三角化。
6. 输出 ASP 风格 4-band `PC.tif`，包含 POINT_OFFSET。

## 速度优化策略

速度优化不能改变 ASP 对齐目标，但可以在 ASP 思路基础上做工程优化：

- 使用 CUDA PatchMatch 作为默认密集匹配实现。
- 缓存灰度图、纹理和 GPU 图像，避免重复上传。
- 对调参阶段支持 ROI 或低分辨率预跑，但最终验收必须全分辨率运行。
- 对三角化、最近邻对比和 mask 处理做多线程或空间哈希加速。
- 对过滤阶段使用线性复杂度或近线性复杂度算法，避免全图高成本重复扫描。
- 保留可配置降采样作为快速预览模式，但严格 ASP 验收模式必须使用全分辨率或经过验证等价的策略。

## 迭代顺序

1. 先抽出结构化 ASP 对比指标模块。
2. 建立可重复基准运行器，记录当前 baseline。
3. 参数化当前过滤步骤，确认覆盖率损失主要发生在哪一步。
4. 优先放松或替换明显过严的过滤：左右深度比例、局部一致性、IQR。
5. 如果覆盖率仍无法接近 ASP，转向补齐极线校正和视差域流程。
6. 当 coverage、median、P95 同时达标后，冻结默认参数。
7. 再更新 GUI dialog 和工作流程入口。

## 测试策略

### 每轮迭代测试

运行基准命令并记录：

- PlaScan valid points。
- ASP valid points。
- coverage ratio。
- NN median。
- NN P95。
- PASS / FAIL。

### 回归测试

保留现有 `stereo_pipeline_test`，但将关键指标从人工日志升级为机器可判断结果。未达标时测试应明确输出失败原因。

### 最终验证

达标后运行：

- ASP 对齐 benchmark。
- terrain / mvs 相关测试。
- GUI 构建。
- GUI 手动验证：打开 dialog，确认入口、文案和输出路径符合预期。

## GUI 更新设计

只有核心 benchmark PASS 后才更新 GUI。

预期 dialog 更新内容：

- 增加“双视图 ASP 对齐模式”。
- 显示输出 `PC.tif` 和 `PC.ply`。
- 显示严格模式/快速预览模式的区别。
- 显示最近一次 benchmark 指标摘要，或提供查看指标报告入口。
- 明确标注该模式当前针对双视图，不冒充通用多视图流程。

## 风险与应对

### 风险 1：严格指标无法靠调参达到

应对：不要继续盲目调参，转向补齐 ASP 风格极线校正和视差域流程。

### 风险 2：覆盖率提升但精度退化

应对：该轮不算成功。必须同时满足 coverage、median 和 P95。

### 风险 3：速度优化破坏质量

应对：所有速度优化必须经过同一 benchmark 验证。快速预览模式不能替代严格验收模式。

### 风险 4：只对单组数据过拟合

应对：第一阶段接受只针对现有测试对达标，但文档和 GUI 文案必须明确范围。后续如需泛化，应追加多组 ASP 基准。
